# Large-phenotype staged JIT screen: bounded metadata cost

The A100 [matched report](../results/staged_device_significant_large_k_probe_20260923/matched.json) screens device-selected significant-pair output on the server-local `/data/zxie3/torchgwas_pgen_benchmark/hardcall_full.pgen` (8,086,101 variants, 22,250 samples, 20,838,552,600 file bytes; `/data` on `/dev/md0` xfs). It declares 600,000 phenotypes, a global spread scenario retaining one in 100 million variant–phenotype pairs, and two layouts over the same unissued frontier: 128-marker chunks with six 100,000-phenotype tiles, or 512-marker chunks with twelve 50,000-phenotype tiles, strided over two GPUs. Both layouts cover every unissued pair exactly once and retain the same 48,510 conditional pairs. Their source and selected-output work is charged on shared resources, including per-GPU device-selector count and launch service.

Eight indexed output events are **simulated** to trigger the existing post-output source stage. No genotype scan, GPU calculation, selection or NPZ write is performed. Decoder, compute, transfer, archive and launch rates are synthetic. The report measures metadata and Python planner cost only; it cannot establish GWAS throughput, a winning tile size or a safe JIT switch. The completed stage used 4.448 CPU and 4.462 wall seconds across eight bounded steps; peak process RSS was 620,652 KiB (606 MiB). Source and benchmark script hashes match the local checkout.

The initial large-K screen took 7.982 CPU seconds. It exposed two calculator limits. First, sparse spread scenarios were capped at a one-million denominator, excluding realistic rare significant-pair regimes. Spread counting now accepts bounded rational denominators up to one trillion using the existing logarithmic floor-sum; clustered placement retains its one-million cap and explicit visit budget. Second, six or twelve phenotype tiles with the same PGEN span and source price repeated the same whole-source pricing. The calculator now hashes each local source profile and prices each distinct span/profile once, while still summing physical read/decode work separately for every tile. The screen reports `unique_priced_source_floors` for audit.

An A/B/B/A control on one completed stage forced the prior repeated pricing by making each cache key unique. Cached screens used 1.012 and 1.660 CPU seconds; forced-no-reuse screens used 4.634 and 5.837 seconds. The respective medians were 1.336 and 5.236 CPU seconds, a 3.899-second (74%) reduction in this matched conditional planner calculation. The forced control includes the same profile hashing as the cached path, so it isolates source-price reuse rather than byte-digest cost. All four runs had the same source-work/partial-floor fingerprint, two evaluated candidates, exact coverage, equal retained-pair counts and mode-specific services. These are same-process planner timings under one shared-server load, not end-to-end GWAS gains.

The final broad A100 suite passed 312 tests across layout composition, source staging, occupancy, the public initial-chunk controller and productive forecasts. The screen still reports `prediction_complete=False` and `selection_validated=False`. Its conditional floors omit some device selector kernels, active/queued work, final publication and a finite output-inclusive completion ceiling. It remains an evidence-only post-output calculation; the public controller does not yet use it to change chunk, tile or GPU ownership.
